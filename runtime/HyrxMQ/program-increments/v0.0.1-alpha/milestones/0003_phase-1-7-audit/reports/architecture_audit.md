## 2. §4 check-by-check evidence

1. **Core → AMQP:** none. Core import closure = `List`, `Buffer`, `BufferView`, `PoolStats`, `Message/MessageID/Envelope`, `Exchange/ExchangeType/Binding`, `Queue/QueueConfig/Delivery`, `Consumer`. No `AMQP`, `vhost`, `broker`, `protocol`, `frame` token in `src/hyrx/core/**` (single product-name occurrence is the docstring `src/hyrx/core/__init__.mojo:1`, see F-9).
2. **Core → TCP/socket/flare:** none. Only `bind` hit is `src/hyrx/core/router.mojo:81` docstring for queue↔exchange binding.
3. **Core → HyrxMQ/broker concepts:** none functional. `publish`/`consume`/`ack`/`prefetch`/`exchange`/`binding` vocabulary exists in core by design — spec §4:225-234 makes the engine the authority for routing, queue state, delivery, acknowledgements and consumer state; that vocabulary is wire-free (`frame` = 0 hits). See F-13.
4. **AMQP → Core:** delegation, not duplication — good. `adapter.mojo:23-95` is a 9-method pure-forwarding shim over `Router` (`declare_exchange/declare_queue/bind_queue/publish/consume/deliver_next/read_payload/acknowledge/reject`), containing no key-matching, no queue state, no delivery bookkeeping. Two caveats: (a) it silently drops protocol arguments (`durable` unused, `adapter.mojo:38-42`; `prefetch` hardcoded 0, `adapter.mojo:69`); (b) it is dead on the network path (F-2).
5. **flare confinement:** complete at import level. Every `from flare` hit in `src/`: `src/hyrx/transport/tcp.mojo:14` (`flare.tcp`), `src/hyrx/transport/tcp.mojo:15` (`flare.net`), `src/hyrx/transport/uds.mojo:14` (`flare.uds`). All remaining 21 `flare` occurrences are comments/docstrings: `tcp.mojo:3,4,7,9,28`, `uds.mojo:3,4,7,9`, `src/hyrxmq/broker.mojo:9`, `src/hyrxmq/amqp_service.mojo:7`, `src/hyrxmq/main.mojo:7,12,84`, `src/hyrxmq/listener.mojo:8,9`, `src/hyrxmq/main_listen.mojo:5,6,10,11`. Matches ADR-0005 `docs/decisions/0005-flare-transport-dependency.md:22-24`. Only one test imports flare directly (`tests/integration/flare_smoke.mojo`, the ADR's verification experiment).
6. **Broker second authority:** none on the live path; one latent. `HyrxMQBroker` holds `_engine` (single `Router` via `src/hyrx/embedded/api.mojo:90`) plus `_adapter` with its own `Router`. `protocol_selfcheck` (`broker.mojo:189-212`) creates `ps-ex`/`ps-q` inside the hidden router and never touches the engine, so that topology is invisible to `status()` (`broker.mojo:155-171`) and to engine counters.
7. **Embedded vs core duplication:** none. `HyrxEngine` wraps `Router` exclusively (`api.mojo:107,111,122,132,140,148,160,166,175`); its own state is 4 telemetry counters (`api.mojo:84-99`) plus `stats()` aggregation (`api.mojo:182-192`). Header claim `api.mojo:6-8` ("No duplicate routing logic. No duplicate queue/exchange structs.") is true. Unused `BufferPool` at `api.mojo:82,91-94` → F-14.
8. **Simulation leakage:** none (see table row 3).
9. **Protocol framing leakage into core:** none — `grep -rni frame src/hyrx/core` → 0 hits. Framing knowledge is confined to `src/hyrx/amqp/frame_codec.mojo` (AMQP wire) and `src/hyrx/transport/framing.mojo` (Hyrx-native wire, see F-4).
10. **§24 transport surface:** below.
11. **§26 management boundary:** below.

## 3. §24 transport-surface verdict

**Verdict: no forbidden messaging verb reaches the transport contract; the contract is nonetheless under-specified, and messaging vocabulary has leaked into the transport *package* (dead code).**

Public surface of the contract types in `src/hyrx/transport/transport.mojo`:

| Struct | Public members | Line |
| --- | --- | --- |
| `TransportConfig` | `max_connections`, `max_frame_size`, `send_buffer_size`, `recv_buffer_size` | `transport.mojo:14-25` |
| `TransportStats` | `bytes_sent`, `bytes_received`, `messages_sent`, `messages_received`, `connections_active`, `connections_total` | `transport.mojo:27-42` |
| `TransportConnection` | `is_connected()`, `disconnect()`, `id()`, `bytes_sent()`, `bytes_received()` | `transport.mojo:44-70` (methods at 57, 60, 63, 66, 69) |

- Forbidden verbs (`publish`, `consume`, `ack`, `route`, `queue`, `exchange`): **0** occurrences in `transport.mojo`. PASS.
- Required verbs `connect`/`accept`/`receive`/`send`/`close`/`address`/`state` exist only on the providers, not on the contract types: `tcp.mojo:50` (`start`/bind), `:84` (`accept_connection`), `:110` (`connect`), `:119` (`send_bytes`), `:127` (`recv_bytes`), `:140` (`recv_exact`), `:157` (`close`), `:162` (`is_connected`), `:71/:77` (`host`/`port` = address); `uds.mojo:42,71,97,105,113,126,143,148,65` mirror them. Per the audit note, provider-level `send_bytes`/`recv_bytes` are receive/send and are allowed. PASS.
- **Leak flagged:** `src/hyrx/transport/framing.mojo:13-23` defines the transport package's wire vocabulary as `FRAME_TYPE_MESSAGE`, `FRAME_TYPE_ACK`, `FRAME_TYPE_REJECT`, `FRAME_TYPE_HEARTBEAT`, `FRAME_TYPE_FLOW_CONTROL`. `ack`/`reject` are acknowledgement semantics that §4:225-234 assigns to the engine and §24:1074-1085 forbids below transport. `src/hyrx/transport/flow_control.mojo:20-42` (`can_send`, `record_send`, `adjust_send_window`, `grant_recv_window`) places backpressure *policy* in transport while §4:233 makes flow-control semantics an engine authority. Both files are production-dead: the only importers are `tests/phase5/framing_test.mojo:4-7` and `tests/phase5/flow_control_test.mojo:3`; `broker.mojo`, `listener.mojo`, `amqp_service.mojo`, `adapter.mojo`, `embedded/api.mojo` import neither. Their existence is announced in `src/hyrx/transport/__init__.mojo:4` ("Phase 5: Network transports (TCP, framing, flow control)") and `docs/TRANSPORTS.md` documents no Hyrx-native wire format at all. → F-4.
- **Contract strength defect:** there is no Mojo trait/interface — `tcp.mojo:32/98` and `uds.mojo:26/85` are independent structs that merely embed `TransportConnection` (`tcp.mojo:101`, `uds.mojo:88`) and duck-type the same method names; `_zeroed` + `recv_bytes` + `recv_exact` are ~50 duplicated lines (`tcp.mojo:20-24,127-155` ≡ `uds.mojo:19-23,113-141`). Nothing structurally stops a future provider from growing a `publish()`/`ack()` method. → F-5.
- **Naming defect:** `TransportConfig.max_frame_size` (`transport.mojo:17`, consumed at `src/hyrxmq/listener.mojo:42`) puts protocol framing vocabulary in the transport config for what is a byte-read cap. → F-6.
- Core coupling: transport imports **nothing** from `hyrx.core`, so providers cannot see message/queue types — correct and stronger than "contract only". → CLEAN.

## 4. §26 management/control-plane verdict

**Verdict: CLEAN today. No management or control-plane code on the hot messaging path.**

- Hot path: `listener.mojo:90-136` (`recv_bytes` → `try_parse_frame` → `handle_frame` → `send_bytes`) → `amqp_service.mojo:195-307` → `broker.mojo` delegates → `HyrxEngine` → `Router`. Per-frame code contains zero status/health/config calls; `status()`/`health()` are reachable only from `listener.mojo:69-73` and `src/hyrxmq/main.mojo:62,69,101,108` (startup/CLI reporting). `HyrxMQConfig.validate()` runs once, at `broker.mojo:78` inside `start()`.
- The management surface is a pure read-only projection over engine counters: `broker.mojo:155-171` → `api.mojo:182-192` → `Router.{queue_count,consumer_count}` (`router.mojo:253-259`), packaged by `src/hyrxmq/status.mojo:8` ("A point-in-time projection of broker state for management/health"). It mutates nothing. INV-012 (`docs/ARCHITECTURE_INVARIANTS.md:56-58`) and `docs/MANAGEMENT.md:79` hold.
- No HTTP/admin/CLI server exists in `src/` (grep `management|admin|http` → docstring/section-label hits only).
- Forward constraint for the future API: `docs/MANAGEMENT.md:22,44` expose `bindings` listing and `docs/MANAGEMENT_API.md:42` permits write actions (purge, delete, disconnect). Those writes must be expressed as calls into the *same* semantic API the data plane uses (`HyrxEngine`/`Router`), never as a second topology table or direct queue mutation, or management becomes a routing authority. Not yet stated in the docs → F-15.

## 5. §34 self-assessment, architecture independence (Q1–Q7)

1. **Did I preserve Hyrx independence from the simulation? — YES.** `grep -rniE "creature|simulation|agent|perception|cognition|motor|world" src/` → 0 hits. INV-006 (`docs/ARCHITECTURE_INVARIANTS.md:28-31`) demonstrated, not inferred.
2. **Did I accidentally make AMQP an internal dependency? — NO for Core; YES-ISH for the product.** Core is AMQP-free (row 1, check 1). But the AMQP translation authority ended up in Layer 5 (`amqp_service.mojo:195-307`) while the Layer-4 adapter is bypassed and carries a private `Router` (`adapter.mojo:20`) → F-2/F-3.
3. **Did I accidentally make TCP mandatory inside Hyrx Core? — NO.** Core imports std + core only; `grep -rn "transport" src/hyrx/core/` → 0 hits; the only TCP/socket material is `hyrx/transport/*` behind `flare` (ADR-0005).
4. **Did I introduce HyrxMQ responsibilities into Hyrx Core? — NO functionally** (no broker lifecycle, vhost, node, status, or config concepts in core; they live in `src/hyrxmq/{config,status,broker}.mojo:28-38,155-171`). Two docstrings claim the product name for library layers → F-9.
5. **Did I introduce premature distributed-system architecture? — NO.** grep `cluster|consensus|distributed|replicat` in `src/` → 0 functional hits (only the word "reflects" in two docstrings). `framing.mojo:19` heartbeat is dead code, not a distribution mechanism. INV-007 intact.
6. **Is Hyrx still usable in-process without networking? — YES.** `hyrx/core` + `hyrx/embedded` depend on nothing but `std` (`api.mojo:10-16`); `HyrxEngine` requires no transport, no flare, no socket. This is the canonical path per INV-002.
7. **Is HyrxMQ still a product built around Hyrx? — YES directionally.** `hyrxmq → hyrx` only; `grep -rn "hyrxmq" src/hyrx/` yields comments (`tcp.mojo:8`, `uds.mojo:8`) and no import. Caveat: `HyrxMQBroker` assembles the engine *and* a parallel adapter/router, which blurs "single Hyrx engine per broker" → F-3.
